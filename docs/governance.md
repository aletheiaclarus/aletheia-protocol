# The Clarus Protocol — Governance

## Purpose

Clarus must be designed so that no single person, government, company, political party, or technical operator can control the system or determine what citizens are allowed to see.

The governance of Clarus should therefore follow the same principle as the protocol itself:

> **Verify, do not trust.**

## 1. No Single Controller

No single organization should have unilateral authority over:

- the protocol rules
- public records
- verification standards
- risk signals
- voting verification
- software releases
- access to public data

Important changes should require transparent and independently reviewable processes.

## 2. Open Development

The core Clarus software and protocol specifications should be publicly documented.

Where practical:

- source code should be public
- proposed changes should be visible
- discussions should be archived
- technical decisions should be documented
- releases should be reproducible

Contributors should be able to inspect how the system works.

## 3. Independent Participants

Clarus should encourage participation from multiple independent groups.

Possible participants include:

- universities
- auditors
- journalists
- civil society organizations
- software developers
- researchers
- public institutions
- independent technical organizations
- citizens

No participant should need to trust another participant completely.

## 4. Separation of Responsibilities

Different responsibilities should be separated where practical.

For example:

- data providers provide source information
- independent verifiers examine the information
- software developers maintain the protocol
- auditors examine the system
- institutions remain responsible for their legal decisions
- citizens and researchers independently examine published evidence

This reduces the risk that one organization can control the entire verification chain.

## 5. Protocol Changes

Changes to the core protocol should be proposed publicly.

A significant change should include:

- the reason for the change
- the problem being addressed
- the proposed solution
- technical implications
- privacy implications
- security implications
- compatibility implications
- relevant alternatives
- testing results

Changes should be reviewed before becoming part of the official protocol.

## 6. Versioning

Clarus should use explicit protocol versions.

A version should not silently change the meaning of previously published records.

Major changes should receive a new version number and a documented explanation.

For example:

- `v0.1` — initial concept
- `v0.2` — expanded protocol design
- `v0.3` — future development
- `v1.0` — stable protocol specification

Early versions are experimental and should not be treated as production systems.

## 7. Transparency of Funding

The organizations or individuals funding Clarus should be publicly disclosed where legally possible.

Funding records should identify:

- source
- amount
- date
- purpose
- relevant restrictions

Funding should not give a contributor hidden control over protocol rules or verification results.

## 8. No Governance Token

Clarus should not require a cryptocurrency or tradable token to participate in governance.

Voting power should never be determined by:

- wealth
- token ownership
- financial investment
- ability to purchase influence

A financial token is not required to create a verifiable public-information system.

## 9. Conflict of Interest

People participating in governance should disclose relevant conflicts of interest.

Examples include:

- financial relationships
- employment
- ownership interests
- contracts
- political or institutional relationships relevant to a decision

A conflict does not automatically invalidate a contribution.

It should be visible so that others can evaluate the decision-making process.

## 10. Security

Security vulnerabilities should have a documented reporting process.

Researchers should be able to report vulnerabilities responsibly.

Security fixes should be reviewed and documented without unnecessarily exposing systems to additional risk.

Critical infrastructure should receive independent security audits before being used in high-stakes environments.

## 11. Electoral Independence

If Clarus is used to support electoral processes, the system must not become the private voting infrastructure of Clarus itself.

Electoral authorities established by law should retain their legal responsibilities.

Clarus can provide:

- verification
- auditability
- cryptographic evidence
- public documentation
- independent checks

It should not give itself authority to declare an election legally valid or invalid.

## 12. Public Accountability

Clarus itself must be auditable.

The public should be able to examine, where practical:

- protocol rules
- software versions
- data sources
- verification methods
- governance decisions
- funding
- security audits
- known limitations

If Clarus makes an error, the error should be documented and corrected transparently.

## 13. Right to Challenge

People and organizations should be able to challenge:

- incorrect data
- incorrect calculations
- inappropriate risk signals
- technical errors
- governance decisions

A challenge should have a documented process and, where appropriate, a public response.

## 14. No Automatic Authority

Clarus should never assume that technical verification gives it legal authority.

The protocol can establish that:

> "According to these sources and these rules, this record appears consistent or inconsistent."

It should not automatically conclude:

> "Therefore this person is guilty."

Legal responsibility remains with the institutions and procedures established by law.

## 15. International Compatibility

Clarus is intended to operate across different countries.

The global protocol should define common technical and transparency principles while allowing each country to implement its own:

- legal framework
- public-data sources
- privacy rules
- institutional responsibilities
- electoral procedures

A country's implementation should not be required to abandon its constitutional or legal framework in order to participate.

## 16. Governance Principle

The governance system should ultimately follow the same philosophy as the protocol:

> **No authority should be trusted simply because it is called authoritative.**

Authority should be accompanied by:

- defined responsibilities
- transparent procedures
- independent oversight
- publicly reviewable evidence
- the ability to challenge decisions

## 17. Evolution

Clarus should evolve through documented experimentation.

The project should prefer:

1. small pilots
2. independent testing
3. public review
4. measurable results
5. documented failures
6. gradual expansion

The protocol should never claim to be finished merely because the software works.

Its governance should remain open to evidence that an assumption was wrong.

---

**Clarus is intended to make public institutions more verifiable. Its own governance must therefore be held to the same standard.**
